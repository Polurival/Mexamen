# Эксперимент: правила v1 → v2 (День 1, Rules)

## Тестовый промпт (один и тот же для обеих генераций)

> Помоги улучшить статистику в приложении: на экране StatsScreen нужно показывать количество пройденных вопросов и количество верных ответов для каждой из тем вопросов. На FlashcardScreen на карточке с правильным ответом, нужно показывать сколько раз этот вопрос юзер уже проходил и сколько раз дал верный ответ. Тоже самое для QuizScreen, точнее в ResultScreen - для каждого вопроса показать сколько раз был пройден, и количество верных ответов

## Протокол (чистое сравнение)

Файлы: `CLAUDE.v1.md` — правила ДО (копия из `HEAD` на момент старта), `../../CLAUDE.md` + `.claude/` — v2.


## Что, по-моему, повлияло на качество

**Честный вывод: на этой задаче правила v2 дали заметно меньше, чем я ожидал.** Обе генерации выбрали одну архитектуру и обошли главную ловушку (гонка записи статистики) — gen1 сделала это без предупреждения в правилах, значит, достаточно было прочитать код.

Что реально сработало (в обоих прогонах):
1. **Существующий код как образец.** `StatsAggregator`/`StatsViewModel`/`RecordAnswerUseCase` уже показывают правильный путь — агент расширил их, а не изобретал новое. Это сильнее любого текста в правилах.
2. **Правило «не рефакторить вне задачи»** (было и в v1): оба diff'а минимальные, ровно 9 файлов.
3. **Единый `QuestionStats` per id** — оба переиспользовали `timesShown/timesCorrect` и не добавляли полей (в v1 этого явного описания нет, но структура очевидна из кода).

Где v2 помог слабо или не помог:
- Антипаттерны и эталонные паттерны почти не изменили результат — модель и так пишет в этом стиле.
- Описание асинхронной записи не дало преимущества (gen1 справилась сама).
- v2 **не предотвратил** протекание data-типа в UI и дублирование литерала — в gen2 они даже хуже, чем в gen1. Правило про data-типы я добавил уже **после** генерации (v2.1, этот PR) — gen2 его не видела.

Что дал сам эксперимент (и попало в правила):
- Обе генерации упали на команде `testDebugUnitTest`: она была в старых правилах, я скопировал её в v2 не проверив. Исправлено на `testAndroidHostTest` / `compileAndroidMain` / `compileKotlinWasmJs` / `:androidApp:assembleDebug`. **Самая ощутимая польза — исправление неверных команд сборки**, а не стилистические правила.
- Добавлены: антипаттерн «data-типы в UI», DRY для строк, обязательный wasm-compile в чеклисте.

Ограничения: n = 1, стохастика модели; задача небольшая и хорошо ложится на существующий код; приложение на устройстве не запускалось, скриншотов нет (UI оценивался по коду).
